Non-Negotiable Requirements

Line-by-line / file-by-file
Every file must be reviewed and listed in an index. If the repo is large, do it in phases, but do not skip files.

Evidence-based
For every claim: include file path + function/component name + line number (or nearest locators if line numbers aren’t available).

No guessing
If something can’t be verified from code, say what evidence is missing and how to obtain it (search terms, runtime logs, reproduction steps).

Prioritize false-signal root causes
The primary goal is to explain why EMA Pullback is producing false signals, and whether the issue is:

indicator calculation

candle alignment/timeframe mismatch

lookback/windowing bug

cache contamination

strategy logic flaw

UI interpretation error

ingestion/normalization issue

Audit Scope (Must Cover All)
A) End-to-End Data Pipeline Trace

Map the complete flow:
Market Data Source → Ingestion → Normalization → Storage/Cache → Indicator Calc → Strategy Calc → Signal Gate → Signal Output → API → UI Display → Journal/History Storage

Identify where data can become:

misaligned (timestamps/timezones/timeframes)

stale (cache not invalidated)

partial (incomplete current candle used)

transformed inconsistently (frontend vs backend conversions)

silently substituted (fallback logic)

B) Indicators & Math Verification (Quant Checks)

Validate:

EMA correctness (formula, smoothing, seed, timeframe consistency)

bar indexing (off-by-one, last candle usage rules)

lookback slicing (window lengths, warmup requirements)

parameter consistency across strategies and modes

precision/rounding issues

C) Strategy Wiring & Execution Path

Confirm:

EMA Pullback strategy is using the expected indicators and bar series

strategy is executed identically in Auto Scan vs Manual Scan

strategy inputs (instrument, timeframe, candles) are consistent and validated

strategy state is isolated (no cross-strategy leakage)

D) Caching & Mode Parity

Confirm:

cache is keyed correctly: strategy + instrument + timeframe + params + barsVersion

no collisions between strategies

no divergence between Auto Scan and Manual Scan paths

cache invalidation happens on new bars, config changes, or param changes

E) UI ↔ Backend Contract & Display Accuracy

Verify:

UI displays the same values the backend computed (no re-derivation drift)

dropdown lists match backend source of truth

signal timestamps and “current bar” interpretation are consistent

history/journal persistence reflects true backend results

F) Observability & Silent Failure Hunt

Identify:

try/catch swallowing

ignored promises

default returns masking errors

missing logging around indicator inputs, gating decisions, final signal emit

Required Output Format (Do Not Change)
1) Executive Summary (1–2 pages)

Most likely root causes of false signals (ranked)

P0/P1/P2 issues

“If we fix only 3 things, fix these” list

Risk statement: how bad could this be in production?

2) Repo Audit Index (Every File Listed)

For every file:

file path

purpose (1–2 lines)

key exports/classes/functions

issues found (if any)

severity (P0/P1/P2)

recommended action: fix / refactor / remove / quarantine

3) Deep Dive: EMA Pullback Strategy Trace

Provide the complete trace:

where candles come from

what preprocessing happens

where EMA is computed

what bars are used (including last candle rules)

how signal triggers (exact conditions)

where gating modifies/blocks it

how output is packaged and displayed

Include: import → call → data transformations → decision points → output.

4) Data Integrity Findings (Proof-Based)

For each integrity issue:

symptom

root cause

proof (file+line)

impact on false signals

fix (specific)

5) Fix Plan (Phased, Execution-Ready)

Phase 0: unblockers (build/typecheck/runtime errors)
Phase 1: correctness fixes (data alignment + indicator math + strategy wiring)
Phase 2: parity & cache hardening (Auto vs Manual, keying, invalidation)
Phase 3: observability + regression prevention (logs/metrics/tests)

Each task must include:

exact files/modules to change

pseudo-diff or code sketch where helpful

tests to add (unit/integration/e2e)

acceptance criteria (how we prove it’s fixed)

6) Verification Protocol (Must Be Reproducible)

how to reproduce the false EMA pullback signal (test case definition)

synthetic candle sequences to validate EMA pullback behavior

checks for bar alignment and last-bar handling

logging/metrics to confirm signals are “clean”

Phased Execution Rules (If Repo Is Large)

If you cannot audit everything in one pass, proceed like this:

Phase A: Inventory & Critical Path

produce full file index

identify critical execution paths (data → indicators → EMA Pullback → signal emit)

audit those first

Phase B: Remaining Files

continue folder-by-folder

maintain a coverage checklist

do not stop until every file is reviewed and listed

At the end of each phase, provide:

coverage status (% files audited)

new critical findings

updated top-priority fix list

Final Objective

Deliver a complete, proof-based audit that answers:

“Exactly where is the data pipeline becoming inaccurate or inconsistent, and which specific code changes will eliminate false signals—especially for EMA Pullback—while preserving system stability?”

Now begin the audit using the repo as the source of truth.
